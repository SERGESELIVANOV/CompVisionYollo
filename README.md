### ONNX Runtime ###

ONNX Runtime — высокопроизводительный рантайм для запуска моделей в формате ONNX на разных платформах и устройствах. Основные преимущества: промежуточный формат модели (ONNX) позволяет переносить обученные модели из PyTorch, TensorFlow и других фреймворков; поддержка аппаратных ускорителей (CUDA, TensorRT, DirectML, OpenVINO и др.); богатые API на C, C++ и Python; гибкая конфигурация сессий и оптимизаций.

Инструкцию по установки библиотеки в проект можно найти на сайтах: 
* Официальная документация и инструкции по установке: https://onnxruntime.ai
* Руководство по сборке и использованию C++ API: https://onnxruntime.ai/docs/build/

ONNX Runtime задумывался как универсальный инструмент для запуска моделей в формате ONNX, но как показала практика использования часто оставляет противоречивые впечатления. С одной стороны, он действительно предоставляет возможность работать с моделями, экспортированными из разных фреймворков, и поддерживает множество аппаратных ускорителей. Однако на практике настройка этой библиотеки оказывается довольно капризной: необходимо тщательно подбирать версии, следить за совместимостью с драйверами и дополнительными зависимостями, а подключение провайдеров вроде CUDA или TensorRT требует отдельной конфигурации и зачастую вызывает ошибки, если окружение настроено не идеально.

Даже после успешной установки производительность не всегда соответствует ожиданиям. На CPU ONNX Runtime может работать заметно медленнее, чем альтернативные решения, а на GPU ускорение не всегда включается автоматически и требует ручной настройки. Первые запуски моделей часто занимают больше времени, чем последующие, что создаёт ощущение нестабильности. В результате библиотека, которая должна была быть лёгким и быстрым решением для инференса, нередко воспринимается как тяжеловесный и требовательный инструмент, требующий значительных усилий для достижения приемлемой скорости работы.

 ## 4. Работа программы ##
Перед началом работы основной программы, создали структуру ModelPreset, в которой содержатся следующие элементы: путь к тегам labels, путь к модели weights, разрешение входной фотографии input_size, минимальный уровень уверенности в определимом моделью, в нашем случае важна скорость, поэтому поставим минимальный 0,5 conf_threshold, и порог для Non-Maximum Suppression, удаление дубликатов 0,45.
Далее загружаем список классов в программу из .names файла с помощью написанной функции loadClassList, далее проверяем поддерживается ли формат изображения с помощью функции isSupportedImage, наша программа поддерживает форматы jpg, jpeg, png, bmp.
После начинается основная часть программы в main. Первоначально настраиваем пути, указываем, где находиться папка с фото, папка куда будут сохраняться результаты выполнения программы. Далее выбирается нужная нам модель, которая будет выполнять детекцию, после воспользовались созданной ранее структурой и создадим предустановленные конфигурации моделей YOLO presets.
Далее программа получает предустановленную конфигурацию по имени в preset_it, и копирует данные в переменную runtime. Устанавливаем пути к папкам для изображений в переменную images_path, для сохранения результатов в output_path.
После с помощью функции getUnconnectedOutLayerNames() получаем имена выходных слоёв. Она содержит характеристики всех слоев, через которые изображение проходит в прямом направлении для получения результатов обнаружения . Далее создаём структуру parms со значениями из runtime размерами входа и порогами фильтрации. И переходим к основной части программы.
Далее с помощью цикла for, проходим по каждой фотографии из выбранной ранее директории, и производим обработку каждой по следующему принципу. Сначала производится подготовка изображения к запуску нейросети, эта функция называется pre_process. Внутри pre_process фото, переводиться в blob, масштабируется и приводится с BRG на RGB с помощью функции blobFromTmage. Далее подаём blob на вход модели с помощью setInput. После создаётся вектор outputs, чтобы сохранялись данные после прохода через модель, далее зарезервируем память для оптимизации кода reserve. С помощью команды forward прогоняем фото через модель. На выходе получаем двухмерный массив, где строки представляют собой количество обнаружений. Первые два значения — это нормализованные центральные координаты обнаруженного ограничивающего прямоугольника. Затем идут нормализованные значения ширины и высоты. Индекс 4 содержит показатель достоверности, который указывает на вероятность того, что обнаружение относится к объекту.
После pred_process следует post_process. В этой функции полученные ранее данные из функции post_process проходят дальнейшую обработку. В функции сначала коэффициенты масштабируются для перевода координат из input_size в размер исходного изображения, далее создали вектора для хранения всех тегов, до применения NMS. После подсчитывается количество классов class_count и количество признаков, признаки для разных моделей разные для yolov5s признаков и есть objectness (показатель достоверности, который указывает на вероятность того, что обнаружение относится к объекту), а у yolov11n нет этого признака, хранятся в переменных expected_with_obj, expectrd_without_obj. Дальше начинаем проходить по всем детекциям находящимся в outputs. В цикле для каждой детекции используем функцию analyzeOutputLayout, которая анализирует размерности выхода модели и определяет формат данных. И преобразуем выход модели в матрицу [детекции x признаки] независимо от исходного формата с помощью функции flattenDetections. Далее определяем наличие objectness и смещение до классовой вероятности, наличие определяется c помощью has_objectness, а смещение переменой class_offset. Далее создаться цикл, в котором будет обрабатываться каждая детекция, в новом цикле читаться координаты ограничивающей рамки cx, cy, width, height, object_conf, для разных моделей он равен разному в yollov5 это objectness в yolov11 считается, что objectness равен одному и прерумяная тоже равна одному. Далее производиться поиск лучшей уверенности модели в классе с помощью ещё одного цикла, лучшая вероятность будет храниться в best_score и итоговая уверенность будет содержаться в параметре confidence и равна objectness * классовая вероятность. Далее происходит преобразование координат, масштабирование, ограничение рамок границами изображения left, top, корректируем ширину и высоту, отбрасываем слишком маленькие рамки. Далее удаляем перекрывающие рамки с помощью NMSBoxes, формируем окончательный результат и только рамки прошедшие NMS, получаем имя класса и возвращаем результат.
Далее рисуются ограничивающие рамки с помощью функции drawDetection на изображении, далее производиться измерение выполнения каждого слоя сети, переводим таймер в миллисекунды t. Далее возвращаем время   обработки с помощью функции getPerfProfile, формируется строка с временем time_label и обрисовывается на изображении с помощью функции putText. Сохраняем фото с названием класса или no_detection если ничего не найдено с помощью функции saveProcessedImage.

## 7. Обучение модели ##
https://docs.ultralytics.com/ru/yolov5/tutorials/train_custom_data/#12-leverage-models-for-automated-labeling

Для обучение модели YOLOv5 использовалась инструкция на сайте выше, для YOLOv11 всё тоже самое за исключением исполняемой команды для запуска процесса обучения
yolo train model=yolov11n.pt data=data.yaml epochs=30 imgsz=640 batch=40
Описание характеристик указано на сайте

Для перевода файла .pt в .onnx была использована встроенная функция библиотеки YOLO:
model.export(
    format='onnx',
    imgsz=640,
    batch=1,
    half=False,
    dynamic=True,
    simplify=True,
    opset=17,
    workspace=4,
    device='cpu'
)
